~/lab · flagship project

Network & Firewall Lab

A home lab I built to learn networking and host security by testing things myself and watching the traffic. An Ubuntu VM in UTM is the server, my Mac is the client, and every conclusion is backed by a packet capture or command output.

status: ongoing 4 labs so far started October 2026

  1. Lab #1 · 9 Oct 2026Wireshark

    HTTP & the TCP handshake

    Question
    What does a web request look like on the wire?
    What I did
    Served a page with python3 -m http.server 8000 on the VM, requested it from the Mac with curl and Safari, read the server log and captured the traffic in Wireshark.
    Key result
    SYN → SYN-ACK → ACK, then GET / → 200 OK, all in plaintext
    Security lesson
    Plain HTTP is readable by anyone on the path, which is why HTTPS matters.
    Read the Lab #1 write-up (opens in a new tab)

  2. Lab #2 · 11 Oct 2026UFW

    UFW firewall: blocked vs allowed

    Question
    What changes when a host firewall blocks a port?
    What I did
    Set UFW to default deny incoming, tested port 8000 blocked and then allowed with ufw allow 8000/tcp, read the UFW logs, captured both cases with tcp.port == 8000 and reverted the changes.
    Key result
    Blocked: only SYN + retransmissions, no reply. Allowed: full handshake + 200 OK. UFW logs show SRC, DST, DPT, PROTO
    Security lesson
    A firewall acts before the application: a dropped port looks like silence, not an error. Default deny, then open only what a service needs.
    Read the Lab #2 write-up (opens in a new tab)

  3. Lab #3 · 13 Oct 2026DHCP · DNS

    Subnetting, DHCP & DNS

    Question
    Where does the VM's network configuration come from?
    What I did
    Practised CIDR and subnet maths, then traced the VM's address, route, resolver and lease with ip addr, ip route, resolvectl, nmcli and dig.
    Key result
    DHCP gave IP, mask, gateway, DNS and a 1-hour lease; 127.0.0.53 is only a local DNS stub
    Security lesson
    Clients trust whatever DHCP and DNS tell them, so a rogue DHCP server or a spoofed DNS answer can silently redirect traffic.
    Read the Lab #3 write-up (opens in a new tab)

  4. Lab #4 · 16 Oct 2026tcpdump

    ARP: from IP to MAC

    Question
    How does the VM find the gateway's MAC address?
    What I did
    Flushed the neighbour cache, pinged the gateway and captured with tcpdump -i enp0s1 arp, comparing ip neigh with the Mac's arp -a.
    Key result
    ARP Request (broadcast to ff:ff:ff:ff:ff:ff) → ARP Reply (unicast), captured in tcpdump
    Security lesson
    ARP has no authentication, which makes ARP spoofing and MITM possible. I studied the defences conceptually: Dynamic ARP Inspection and DHCP snooping. HTTPS and VPNs keep data encrypted but don't stop the spoofing.
    Read the Lab #4 write-up (opens in a new tab)
